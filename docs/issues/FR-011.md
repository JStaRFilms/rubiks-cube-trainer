# FR-011: Cross+2, feasibility gated

## User story
Practice cross plus two distinct F2L pairs only if bounded generation supports the approved goal on target devices.

## Proposed flow
First prototype explicit two-pair goals and valid heuristics; measure range, hit rate, resource cost and difficult requests. B12 reports supported limits. B13 implementation starts only after passing evidence and explicit owner go.

## Technical considerations
Follow [PLAN.md §4.6](../imports/PLAN.md). Do not extrapolate Cross+1 or build large tables by assumption. Validate witnesses against full cube state. A sequential substitute changes product scope and is not authorized.

## Dependencies
B12 after Q06; B13 also needs owner go; Q05 review is planned. Requires FR-002/003/004 and shared Cross/Cross+1 contracts.

## Acceptance criteria
- Feasibility evidence covers varied depths/caps and hard requests, validated witnesses, bounded runtime/memory and honest failure limits.
- Integration offers only supported ranges and each result solves cross plus two distinct pairs within L.
- Cancellation/timeouts are safe; no weaker challenge is returned.
- Failed feasibility leaves the trainer visibly undelivered. No implementation before owner go.
